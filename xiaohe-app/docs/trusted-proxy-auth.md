# 正式代理签名断言：部署适配与验收

当前集成分支的正式模式不是旧版身份头的直接兼容实现，尚未对接真实代理。上线前须完成代理适配、安全审查和隔离环境端到端验证；本文件不执行部署。

## 模式与配置

- `AUTH_MODE=demo`：仅接受应用签发的 `__Host-xiaohe_demo` Cookie；需要独立的 `DEMO_SESSION_SECRET`。演示身份不能邀请或修改成员。
- `AUTH_MODE=trusted-proxy`：仅接受代理签名断言；需要 `PROXY_ASSERTION_SECRET`、`PROXY_ASSERTION_ISSUER`、`PROXY_ASSERTION_AUDIENCE`。密钥须使用独立高熵随机值并通过部署平台的安全机制配置，不能放入源码或客户端。
- 未设置或其他值：认证关闭并拒绝身份；请求头、查询参数和请求体不能选择模式。两种模式不会互相回退。

## 代理必须实现的协议

1. 代理先通过自己的可信认证系统核验用户；删除客户端提交的 `x-xiaohe-proxy-assertion` 与所有上游身份头，绝不能把用户提供的值作为身份依据。
2. 每次上游请求重新签发 `x-xiaohe-proxy-assertion`：紧凑 JWT，header 为 `{"alg":"HS256","typ":"JWT"}`。用与应用一致的 HMAC-SHA256 密钥签名；密钥仅供代理和应用服务端读取。
3. payload 必含字符串 `iss`、`aud`、`sub`、`email` 与整数 Unix 秒 `iat`、`exp`；可选 `name`。`iss`、`aud` 必须与应用配置完全一致；`sub` 为稳定身份且不得以 `demo_` 开头。最长有效期 60 秒，应用允许签发时间最多超前 5 秒，过期即拒绝。角色不接受代理断言指定，而由服务端工作区成员关系决定。
4. 上游使用受保护的 TLS 通道；限制对应用源站的直接访问，并避免在访问日志、追踪、错误信息和客户端泄露断言。该断言是 bearer 凭据，当前实现未绑定请求或实现一次性 nonce；泄露后在有效期内可重放。应通过网络隔离、密钥管理和短有效期降低风险，并由安全负责人决定是否需要防重放机制。
5. 代理须提供实际的 `/signin-with-chatgpt` 和 `/signout-with-chatgpt` 流程，并在经过认证后的所有应用请求上注入断言。应用本身不实现代理登录页面或身份提供商。

## 与旧版不兼容之处

旧版信任 `oai-authenticated-user-id`、`oai-authenticated-user-email`、`oai-authenticated-user-full-name` 等头；当前正式模式忽略它们。仅设置 `AUTH_MODE=trusted-proxy` 而不部署签名适配器会导致登录失败；不能通过恢复对公网请求头的信任来解决。部署时还须确认代理身份 `sub` 与历史工作区用户 ID 一致，否则用户会进入新空间，原有数据不会自动迁移。

## 上线前验证

在隔离环境核对代理正常登录、退出、过期和刷新；伪造旧身份头、无签名、错误密钥、发行方/受众错误、过期断言均拒绝。用两个真实隔离身份验证邀请、工作区选择、跨角色访问、作者与审核人分离及文件隔离；确认日志无断言与密钥。当前分支只完成签名校验单元测试，尚无真实代理联调或完整端到端证明。
